# story-work — 손으로 했던 디자인 작업 흐름

> "실제로 어떻게 했는지"의 기록. 판정 기준(story-service.md의 N1·N2)과 섞지 않음.

## 작업 흐름 (실제 순서)
1. 나는 uibowl에서 경쟁사 레퍼런스를 수집한다.
2. 나는 레퍼런스를 분석하고 우리 서비스에 반영할 부분을 가져온다. ⏸
3. 나는 분석 내용을 토대로 화면 설계 문서를 구체화한다.
4. 나는 Figma에 레퍼런스와 화면 설계서를 반영한 키스크린 2~3개를 390×844로 그린다.
5. 나는 내부 관계자와 협의한 후 컨셉 시안을 확정한다.
6. 나는 확정 시안으로 디자인 토큰과 컴포넌트를 만들고 화면 디자인을 한다.
7. AI가 완성 시안의 토큰·컴포넌트가 가이드를 위반했는지 검토한다. ⏸

## 산출물 (명사)
| 단계 | 산출물 |
|---|---|
| 1 | 경쟁사 레퍼런스 모음 |
| 2 | 레퍼런스 분석 (반영할 부분 목록) |
| 3 | 화면 설계 문서 |
| 4 | 키스크린 2~3개 (Figma, 390×844) |
| 5 | 확정 컨셉 시안 |
| 6 | 디자인 토큰, 컴포넌트, 완성 화면 디자인 |
| 7 | 가이드 위반 검토 결과 |

## 멈칫 (게이트 위치)
| 단계 | 이유 | 실패 시 복귀 |
|---|---|---|
| 2 | 반영할 부분을 고르는 기준이 없음 | → 1 |
| 7 | 가이드 위반 여부 판정 | → 6 또는 4 |

## 넘김 (에이전트 경계)
| 지점 | 넘어가는 곳 | 종류 |
|---|---|---|
| 1 | uibowl | 도구 |
| 4, 6 | Figma | 도구 |
| 5 | 내부 관계자 (협의만, 확정은 본인) | 사람 — 협의는 하네스 밖에서 진행 |
| 6 → 7 | 나 → AI | 주어 변경 |

## 하네스 반영 메모
- "키스크린 2~3개" → 하네스에서는 화면 1개 = 실행 1회, S1~S3 세 번 실행
- 5단계 관계자 협의는 하네스 밖에서 하고, 하네스에는 본인 승인만 기록
